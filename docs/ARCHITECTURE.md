# ARCHITECTURE — Moscow Live

> CTO-документ. Дата: 27.11.2026. Цены и лимиты — на дату; ссылки на первоисточники в конце. Непроверенное помечено `[не проверено]`.

## 0. Решение

- **MVP без бэкенда.** Статика + 3 «живых» JSON; обновление — GitHub Actions cron. Ни БД, ни API-сервера, ни WebSocket.
- **Погода/ветер и воздух — прямо из браузера** (CORS, без ключа): нулевая инфраструктура, данные всегда свежие.
- **Данные Москвы (ордера/разрешения) — только через cron:** ключ data.mos.ru нельзя отдавать клиенту.
- **Пробок и афиши в MVP нет:** бесплатного легального источника нет (см. §1).

## 2. Архитектура MVP

```
Open-Meteo API ──(fetch из браузера)──────────────────────────┐
data.mos.ru ──► GH Actions cron ──► validate ──► live/*.json ──┤
OSM/PMTiles (GitHub Release) ──► существующий пайплайн ───────┤
                                                              ▼
                       GitHub Pages: Next.js static + PMTiles + /live
                                                              │
            MapLibre: слои + «данные на HH:MM» + last-good fallback
```

- **Остаётся статикой:** здания/скоры, деревья, POI, PMTiles, UI, адресная карточка. Пересборка — только при изменении кода или раз в месяц.
- **Требует обновления:** `live/air.json`, `live/works.json`; погода — без файла, напрямую из API.
- **Бэкенд не нужен.** Воркер/кэш тоже: кэш — HTTP-кэш браузера + last-good JSON в артефакте. Минимальная единица — cron-джоба + JSON-контракт.
- **Контракт:** `live/meta.json` = `{generated_at, stale, sources:{...}}`; файлы с `?v=<hash>` — на Pages нельзя задать `Cache-Control`, поэтому версия в URL.
- **Деградация:** последний валидный JSON не удаляется; слой показывает «данные от HH:MM», при `stale>24ч` скрывается с пояснением. Пустой карты не бывает.

### 2.5 Контракт слоя

Слой — плагин из `web/app/layers/contract.ts`, а не импорт в `map.tsx`: карта
читает только реестр (`layers/registry.ts`) и общий `visible`, поэтому новый
слой не требует правок в `map.tsx`.

- **Из чего состоит:** `id`, `label`, `defaultVisible`, необязательный
  `visibilityKey` (чип в панели), `mount(context)` → `LayerHandle` /
  `unmount()`, хуки `onTimeChange(minutes)`, `onWeather(snapshot)`,
  `onTheme(theme)` и `View({context})` — UI слоя (плашка, бейдж).
- **Что ему дают:** `getMap()` (карта MapLibre или `null`, пока она создаётся),
  `theme` (`data-theme`), `time` (выбранные минуты + текущие МСК), `weather`
  (снимок Open-Meteo на час: `get`/`at`/`subscribe`), `facts`
  (`live/meta.json`: статус, дата, признак устаревания).
- **Что он обязан отдать:** в `unmount` снять всё, что поставил (источники,
  слои, слушатели, таймеры, `AbortController`); не трогать чужие слои; не
  дублировать запросы, данные которых уже есть в контексте; честно писать
  «нет данных», а не пустоту.

**Новый слой за 5 шагов** (пример — «Заведения»): 1) `layers/places.tsx` —
`LayerPlugin` с `id: "places"`, `label: "Заведения"`, `defaultVisible: false`,
`visibilityKey: "places"`; 2) `mount` — источник и слой POI; 3) `unmount` —
снять их и слушатели; 4) `onTheme`/`onTimeChange` — перекраска и пересчёт;
5) добавить в `LAYERS` (`registry.ts`) и чип в `layers-panel.tsx`.

## 4. Обновление данных

| Поток | Чем | Частота | Бюджет |
|---|---|---|---|
| Погода/ветер | браузер → Open-Meteo | 30 мин (модель 1 ч) | 1 запрос на пользователя/30 мин; квоты считаются на IP клиента |
| Воздух-прогноз | браузер → Open-Meteo AQ | 60 мин | то же |
| Ордера, разрешения | GH Actions → data.mos.ru | 1×/сут, 06:00 MSK | 1 запуск ≈ 1–2 мин, $0 (public repo) |
| POI, деревья, здания | существующий Python-пайплайн | 1×/мес | вручную/по расписанию |

- **Почему не «каждые 5 минут»:** cron GitHub Actions — best-effort и может опаздывать; в public-репо отключается после 60 дней без активности; Pages — 10 деплоев/ч.
- **Данные ≠ деплой сайта:** live-workflow коммитит только `live/*.json` в `gh-pages`, без tippecanoe/Playwright/Next-сборки. Иначе 10-минутный таймаут и 10 сборок/ч.
- **Если источник умер:** 3 retry с backoff → schema-validate → оставить last-good → `stale=true` → бейдж в UI + авто-issue. Через 24 ч слой скрыть с текстом «источник недоступен».
- **Если сломался cron:** daily-коммит, вероятно, сбрасывает 60-дневный таймер `[не проверено]`; weekly-canary проверяет `meta.json` и создаёт issue.

## 5. Технические риски

| Риск | Механика | Триггер | Ответ |
|---|---|---|---|
| Квоты и ключи | Open-Meteo 10k/сут на IP; лимит data.mos.ru не документирован; 401/429 | 3 подряд 429/401 или >5% ошибок за запуск | last-good + алерт; ключ только в Secrets |
| Трафик и размер | 100 ГБ/мес soft; 1 ГБ сайт; 10 деплоев/ч; первый визит = PMTiles + JSON (размер снять в DevTools) | >70 ГБ/мес, >8 деплоев/ч, сборка >8 мин | переезд на Cloudflare Pages |
| Свежесть | cron best-effort, 60-дневное отключение, задержка публикации Pages | нет успеха 2 интервала подряд (2 ч / 26 ч) | stale-бейдж, last-good, авто-issue |
| Юридика | ODbL (атрибуция + share-alike), Open-Meteo non-commercial, условия Яндекса ограничивают хранение/кэш `[не проверено]` | монетизация / релиз без атрибуции / платный слой | блок релиза; лицензия или удаление слоя |

## 6. Чего нельзя на этом этапе

- Показывать пробки без лицензии Яндекса/ЦОДД; парсить Яндекс, ЦОДД или mosecom в обход условий.
- WebSocket/SSE, «real-time каждые 5 секунд»: нет источника, нет потребителя, нет SLA.
- Свои датчики, краудсорсинг и пользовательские метки без модерации и юридической базы.
- Выдавать модель CAMS за замер; публиковать концентрации/децибелы как факт.
- Бэкенд, БД, auth, личные кабинеты «на будущее» — до платного потока или >10k DAU.
- Обещать точность ветра «до двора»: сетка модели 1–11 км.
- Коммитить `data.zip`/PMTiles в git (лимит 1 ГБ, история раздувается).
