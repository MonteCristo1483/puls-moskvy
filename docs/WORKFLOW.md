# WORKFLOW — как работает команда агентов

Короткий устав. Если правило противоречит задачи — правило важнее, задачу переформулировать.

## Роли

- **Владелец** — видение, приёмка, вкус. Не программист.
- **Оркестратор (CTO)** — решает «что делать», ставит брифы, принимает результат, пишет документы. Код руками не пишет.
- **Исполнители** (`web`, `pipeline`, `general`) — делают одну задачу в одной сессии, отчитываются ≤12 строками.
- **Researcher** — проверяет факты и источники, ничего не меняет.

## Правило одной сессии

Одна задача — один бриф — один отчёт. Задача, которая не влезает в сессию, режется, а не «дожимается».

Бриф ≤120 строк, отчёт ≤12. В отчёте — только цифры и вердикты: без диффов, логов и простыней.

## Git

- `git status -uno` вместо `git status` (папка в OneDrive).
- Коммит только `git commit --no-status`.
- Работа — в ветке от актуального `origin/main`; имя ветки = тип задачи (`fix/`, `feat/`, `docs/`, `data/`).
- **Не пушить в `main`.** Пуш ветки запускает Autopilot, который сам мержит и деплоит — поэтому пушим только готовое и проверенное.
- Запрещены force-push и `npm run deploy`.

## Данные

- Бинарники (`.pmtiles`, `*.zip`, `data/raw`) в git не попадают.
- Данные публикуются ассетом `data.zip` в Release; Deploy распаковывает их в `web/public/data`.
- Деплой данных — только вместе с кодом, который их понимает. Сначала проверить совместимость схемы, потом лить.

## Качество

Перед «готово»:
1. типы (`tsc --noEmit`) и сборка;
2. тесты (юнит/пайплайн) и golden, если менялись данные;
3. проверка на проде после деплоя — конкретным действием, а не «вроде ок».

## Экономия

- Модель по умолчанию — `opencode-go/deepseek-v4.1-flash#high`. Дороже — только при доказанной необходимости.
- В контекст оркестратора не льём код, диффы и логи — только цифры.
- Дорогие операции (пересборка тайлов, заливка 200+ МБ) — батчить.

## Документы

- `docs/BRIEF.md` — общий контекст проекта.
- `docs/PRODUCT.md` — позиционирование и MVP (владелец документа: product).
- `docs/ROADMAP.md` — вехи и приёмка (владелец: delivery).
- `docs/ARCHITECTURE.md` — данные, хостинг, риски (владелец: CTO).
- `docs/DECISIONS.md` — журнал: дата — решение — почему. Только дописывать.
- `docs/CONTEXT.md` — карточка состояния на 20 строк, обновляется в конце каждого блока работ.
